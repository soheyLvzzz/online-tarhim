# گزارش مرحله‌ای فاز ۶ آنلاین ترحیم

تاریخ: ۳۱ اکتبر ۲۰۲۶. مبنا: سورس نسخهٔ ۱۷ و خروجی فازهای ۴ و ۵. شروع فاز ۶ با درخواست صریح کاربر است. فازهای ۱ تا ۳ باز نمی‌شوند. هدف، نسخهٔ اول استاتیک و تماس مستقیم روی هاست موجود است.

## بررسی‌های انجام‌شده

تطابق package.json و lockfile، تطابق هر شش وابستگی مستقیم نصب‌شده با lockfile، npm run check، npm run build و python3 scripts/make-preview.py بررسی یا اجرا شدند و موفق بودند. تست‌های hook پنج مورد و تست‌های preview دو موردند. خطای هشدار تنظیم http-proxy در npm مانع موفقیت فرمان‌ها نشد.

در مقایسهٔ بسته‌بندی، فایل‌های src و public با نسخهٔ ۱۷ سنجیده می‌شوند؛ تفاوت ظاهری یا منطقی عمدی نداریم. موارد تغییرکردهٔ توسعه شامل .gitignore، .env.example، .node-version، scripts و engines در package.json، metadata هماهنگ engines در package-lock.json و مستندات است. نسخهٔ هیچ وابستگی تغییر نکرده است.

## اطلاعات موردنیاز

فهرست کامل در required-inputs.md است: دامنه، شرکت/پنل هاست، مسیر دامنه، نشانی و سطح دسترسی Staging، روش انجام عملیات و مقصد مخزن. رمز یا توکن در چت لازم نیست. سؤالات محتوا و شمارهٔ تماس به فازهای وابسته مربوط‌اند و برای این فاز دوباره پرسیده نمی‌شوند.

## دروازهٔ عبور

فاز ۶ در حال انجام است و کامل اعلام نمی‌شود. تا ایجاد و بررسی Staging و مشخص‌شدن وضعیت مخزن، خروجی‌های لازم این فاز کامل نیستند. وارد فاز ۷ نشدیم. بستهٔ تحویلی گزارش پیشرفت و محیط توسعه است، نه نسخهٔ منتشرشده یا گزارش عبور قطعی فاز.

## پیگیری پاسخ‌ها و راهنمای عملی

دامنه onlinetarhim.com، پنل cPanel و مسیر public_html از کاربر دریافت شد. کاربر خودش بارگذاری را با راهنمایی انجام می‌دهد و مخزن شخصی GitHub می‌سازد. مسیر /staging/ به‌عنوان محیط آزمایشی جدا پیشنهاد و بستهٔ Upload مخصوصش آماده شد. راهنمای Private repository و Upload فایل‌های استخراج‌شدهٔ سورس تهیه شد. این‌ها آماده‌سازی هستند؛ خود محیط آزمایشی، مخزن GitHub، دسترسی HTTPS و محتوای روی هاست هنوز تأیید نشده‌اند و فاز ۶ باز می‌ماند. هیچ remote/push یا تغییری در فایل‌های هاست انجام نشده است.

بستهٔ Staging متای noindex,nofollow دارد که فقط برای عدم فهرست‌شدن در موتور جستجو است، نه کنترل دسترسی. برای ریشهٔ نهایی نباید این بسته را استفاده کرد. فایل‌های عمومی از سورس و اسناد توسعه جدا تحویل می‌شوند.

## رخداد ۴۰۳ پس از استخراج توسط کاربر

کاربر وجود فایل‌ها در public_html/staging و پاسخ ۴۰۳ را گزارش کرد. بازکردن مستقیم URLها از ابزار وب ممکن نشد؛ وضعیت هاست مستقلاً تأیید نشد. بررسی ZIP ارسالی مشخص کرد index.html با ZipFile.writestr به‌صورت پیش‌فرض مجوز 0600 گرفته بود، در حالی که JS و CSS برابر 0644 بودند. این خطای بسته‌بندی عامل است؛ وجود همین مجوز روی هاست هنوز مشاهده نشده و علت قطعی ۴۰۳ ادعا نمی‌شود. بستهٔ اصلاح‌شده با تمام فایل‌های 0644 و پوشه‌های صریح 0755 تهیه و مجوز تمام ورودی‌ها و برابری بایت‌های محتوایی با بستهٔ قبلی بررسی شد.

اولین اقدام پیشنهادی کاربر: فقط مجوز public_html/staging/index.html را از File Manager بررسی و در صورت نیاز 0644 کند و URL فایل مستقیم را باز کند. اگر خطا باقی ماند، مجوز فعلی staging و خط مرتبط در Metrics/Errors درخواست شود. تغییر مجوز ریشهٔ public_html، 0777 یا حذف .htaccess تجویز نمی‌شود. فاز ۶ تا مشاهدهٔ نسخهٔ آزمایشی صحیح باز است.

## به‌روزرسانی محیط آزمایشی و تغییر رنگ کارنامه

کاربر اعلام کرد پس از استفاده از بستهٔ اصلاح‌شده سایت بالا آمده است و مقدار دسترسی را ۷۵۵ گذاشته است؛ مشخص نکرد این مقدار برای فایل بود یا پوشه. نتیجه به‌عنوان تأیید کاربر برای اجرای محیط آزمایشی ثبت شد، نه مشاهدهٔ مستقیم عامل. مراحل ۶٫۹ و بخش اجرای آزمایشی ۶٫۱۰ طبق گزارش کاربر آماده‌اند. Git محلی و خروجی محیط توسعه موجودند. ایجاد GitHub و ثبت سورس روی آن هنوز گزارش یا تأیید نشده و remote نداریم. چون کاربر مخزن GitHub خواسته، همین اقدام باز باقی است؛ فاز ۶ هنوز نهایی بسته نشده و فاز ۷ آغاز نشده است.

تنها تغییر ظاهری درخواستی: background در TrackRecord.css از #121212 به #000000 تغییر کرد. git diff پیش از commit نشان داد فقط همین فایل در src/public تغییر دارد و مقایسهٔ متن، تنها همین مقدار را تأیید کرد. build شامل TypeScript موفق بود؛ پیش‌نمایش مستقل بازسازی شد. بستهٔ Staging با مجوز فایل 0644 و پوشه 0755 و متای noindex ساخته شد. وجود فایل‌های build قدیمی در dist مانع نیست: ارجاع دقیق stylesheet در HTML کنترل شد و همان stylesheet پس‌زمینهٔ مشکی دارد. محتوای فایل‌های build قبلی در HTML انتخاب نشده است. هیچ فایل روی هاست توسط عامل تغییر نکرده و اثر رنگ جدید روی هاست منتظر بارگذاری کاربر است.

## آیکون تب و انتقال دستی به ریشه توسط کاربر

کاربر اعلام کرد فایل‌ها را در public_html ریشه گذاشته تا دامنه خالی نباشد؛ این جابه‌جایی توسط عامل انجام نشده و حفظ staging فعلی هنوز پرسش باز است. درخواست آیکون تب با خود فایل logo.png سفید بدون ویرایش تصویر انجام شد: public/favicon-white.png کپی بایت‌به‌بایت لوگو و link rel=icon در index.html اضافه شدند. query v=1 برای نشانی جدید آیکون ثبت شد. کد هیچ سکشن و فایل دارایی قبلی تغییر نکرد.

build شامل TypeScript موفق بود؛ dist با --emptyOutDir ساخته شد. بستهٔ مخصوص ریشه بدون noindex آزمایشی تهیه شد و فایل‌ها 0644 و پوشه‌ها 0755 دارند. وجود ارجاع آیکون، برابری بایت لوگو، لینک‌های index و سلامت ZIP بررسی شدند؛ تغییر favicon در مرورگر هاست هنوز تأیید نشده است. noindex حذف‌شده مربوط به HTML بستهٔ Staging قبلی است؛ تنظیم header/robots سمت هاست مستقلاً بررسی نشده است.

برای بستن فاز ۶، ثبت سورس به‌روز در GitHub شخصی مورد درخواست کاربر و قابل‌استفاده‌ماندن محیط آزمایشی جدا بررسی می‌شود. صرف ایجاد مخزن خالی کافی نیست؛ دسترسی/شواهد فایل‌ها و commit لازم است. برای راهنمایی، URL مخزن و خالی یا دارای‌فایل‌بودن آن کفایت می‌کند. اگر Private باشد و عامل دسترسی ندارد، تأیید کاربر یا تصویر صفحهٔ فایل‌ها بدون اطلاعات محرمانه می‌تواند ثبت شود؛ مشاهدهٔ مستقل ادعا نمی‌شود. رمز، توکن یا دعوتِ حدس‌زده لازم نیست. فاز ۷ آغاز نشده است.

## بررسی مستقیم favicon در صفحهٔ منتشرشده

کاربر مخزن https://github.com/soheyLvzzz/online-tarhim را ساخته و خالی‌بودن آن را اعلام کرد؛ این صرفاً تأیید کاربر است، نه مشاهدهٔ محتوای مخزن خصوصی. ارسال فایل یا push توسط عامل انجام نشده است. کاربر صریحاً می‌گوید دیگر نسخهٔ staging ندارد و سایت در ریشه است؛ بنابراین خروجی محیط آزمایشی جدا فعلاً موجود نیست و فاز ۶ کامل اعلام نمی‌شود.

در مرورگر عمومی https://onlinetarhim.com/ و https://onlinetarhim.com/index.html هر دو باز شدند. DOM هر دو هیچ link[rel*=icon] نداشت و meta robots برابر noindex,nofollow بود. CSS به assets/index-CniwzCQp.css و اسکریپت به assets/index-scVGBm8x.js ارجاع داشت. بنابراین صفحهٔ واقعاً نمایش‌داده‌شده با HTML خروجی جدید دارای favicon یکسان نیست؛ علت اینکه مرورگر نماد عمومی را نشان می‌دهد، صرفاً به کش favicon نسبت داده نمی‌شود. دلیل اینکه نسخهٔ قدیمی HTML روی هاست ارائه می‌شود (جایگزین‌نشدن، cache یا تنظیمات) هنوز جداگانه تأیید نشده است.

در سورس فقط href آیکون به favicon-white-v2.png?v=2 تغییر کرد و فایل جدید کپی بایت‌به‌بایت لوگوی سفید اصلی است. build و TypeScript موفق بودند. بستهٔ کوچک اصلاح فقط index.html و favicon-white-v2.png دارد و همان CSS و JS مشاهده‌شده روی هاست را ارجاع می‌دهد؛ هیچ سکشن تغییر نکرده است. بستهٔ سورس به‌روز و نسخهٔ آزمایشی جدا برای اقدام خود کاربر آماده شدند. پس از بارگذاری، وجود link آیکون و قابل‌نمایش‌بودن فایل باید دوباره بررسی شود؛ نمایش نهایی آیکون در تب پیشاپیش تأیید نمی‌شود.
