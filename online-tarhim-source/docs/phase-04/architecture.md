# معماری انتشار اول لندینگ آنلاین ترحیم

این سند فقط انتشار اول معرفی و تماس مستقیم را پوشش می‌دهد. سند فناوری‌های منتخب در technology-decisions.md و فهرست نسخه‌های مشاهده‌شده در dependencies.json قرار دارند.

## جریان اجرا

در محیط توسعه، Vite و TypeScript سورس React و CSS را به فایل‌های قابل انتشار در dist تبدیل می‌کنند. محتوای پوشهٔ dist به مسیر عمومی هاست فعلی منتقل می‌شود. مرورگر فایل‌ها را از دامنه دریافت و رابط را اجرا می‌کند. لینک tel تماس را به برنامهٔ تماس دستگاه می‌سپارد و ایمیل از mailto استفاده می‌کند؛ این‌ها در سایت سفارش ذخیره نمی‌کنند.

HTML مستقل OPEN-online-tarhim-v17.html برای بازبینی آفلاین است. فایل تحویل انتشار باید بر مبنای dist و دارایی‌های کنار آن باشد تا HTML و باندل‌ها و فایل‌های عمومی به‌صورت مستقل و قابل کش ارائه شوند. سورس، node_modules و اسناد داخلی نباید به پوشهٔ عمومی هاست منتقل شوند.

## مرز ماژول‌ها

| مسیر | مسئولیت |
| --- | --- |
| src/components | Header، Hero، About، Plans، Services، Archive، News، TrackRecord و Footer؛ اجزای ظاهری مستقل و callbackهای تعامل. |
| src/main.tsx | مونتاژ صفحه و اتصال تعاملات؛ CustomEventهای فعلی محل اتصال آینده‌اند، نه API. |
| src/hooks/useScrollReveal.ts | ورود آرام و یک‌بارهٔ سکشن‌ها و رعایت کاهش حرکت سیستم؛ کارنامه از آن استفاده نمی‌کند. |
| src/styles.css و motion.css | قاب صفحه، قواعد مشترک و حرکت‌های فعلی. |
| public/assets و public/fonts | تصاویر، SVG و فونت‌های محلی. |
| scripts | ساخت و تست پیش‌نمایش مستقل و تست منطق ورود؛ در اجرای سایت روی هاست نقشی ندارند. |
| docs و AGENTS.md | تصمیم‌ها، منابع و شیوهٔ ادامه؛ برای توسعه، خارج از پوشهٔ عمومی انتشار. |

## داده و عملکرد

داده‌های فعلی سکشن‌ها در سورس ثابت‌اند. در این انتشار به API، ORM یا لایهٔ ذخیره‌سازی سفارش نیاز نیست. تغییر محتوای ثابت مستلزم اصلاح سورس و ساخت دوباره است؛ پنل و CMS وعده داده نمی‌شود.

کاربر ثبت درخواست از طریق تماس را پذیرفته است. تبدیل دکمهٔ درخواست مراسم/انتخاب پلن به مسیر تماس در فاز ۹ و پس از تعیین شمارهٔ اصلی انجام می‌شود. برای کنترل‌های مقاله، پخش مراسم، منو و شبکه‌های اجتماعی باید مقصد واقعی یا رفتار تأییدشده تعریف شود. هیچ مقصدی در این فاز تغییر نکرده است.

## توسعهٔ بعدی

کامپوننت‌های ظاهری تا حد ممکن حفظ می‌شوند و callbackها در آینده می‌توانند به مسیر و فرم واقعی متصل شوند. اضافه‌شدن فرم ثبت درخواست، احراز هویت، پرداخت، مدیریت مراسم یا ذخیرهٔ اطلاعات، نیازمند بررسی مجدد معماری مرتبط و طراحی قرارداد داده و API در مراحل مربوط است. انتخاب NestJS، PostgreSQL یا Prisma صرفاً از روی پیش‌فرض اسکیل برای آینده نهایی نمی‌شود.

## موارد باقی‌ماندهٔ انتشار

عرض حداقل ۱۴۴۰ پیکسل فعلی برای تجربهٔ موبایل کافی نیست. کنترل‌های بی‌مقصد، محتوای نمایشی، شمارهٔ اصلی تماس، مرورگرها، RTL، سئو و بررسی نسخهٔ آزمایشی باید در فازهای مربوط رسیدگی شوند. برای استقرار، از فایل‌های هاست قبلی پشتیبان گرفته شود و روش بازگرداندن فایل‌ها مشخص باشد؛ این سند به معنی اجرای این اقدامات نیست.
